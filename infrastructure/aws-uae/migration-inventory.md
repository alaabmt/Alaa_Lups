# جرد أنظمة نَحْنُ قبل أي انتقال إلى AWS الإمارات
**تاريخ:** 11 أكتوبر 2026 | **لا تنسخ بيانات المستخدمين إلى GitHub أو إلى هذا الملف.**

## 1. الأنظمة القائمة
- **الواجهة العامة:** GitHub Pages، المستودع `alaabmt/Alaa_Lups`، النطاق `na7nlupus.com`. يمكن إبقاء المحتوى العام هنا عند تشغيل خلفية صحية إماراتية.
- **الحساب والتسجيل:** `na7n-auth.js` و`na7n-account.js`، نظام Supabase Auth؛ معرفات المستخدمين والجلسات والمصادقة الثنائية لها اعتماد وظيفي لا ينقله `pg_dump` وحده.
- **ملفات الحساب:** `public.na7n_profiles` (اسم، هاتف، ربط بالمستخدم). هذه **بيانات شخصية**؛ يجب نقلها وفق الأساس القانوني المعتمد فقط.
- **المتابعات الأخرى:** `public.na7n_assessments` و`public.na7n_responses`، و`na7n-checkin.js`. قد تتضمن معلومات صحية فعلية إذا استخدمها أحد؛ لا نفترض أن كل بيانات النظام وهمية؛ يلزم التدقيق والفرز قبل أي تصدير.
- **الاستبيان Q-SLAQ:** `q-slaq.js`، حفظ تشفيري محلي اختياري `na7n-q-slaq-device-vault.js`، وعرض محلي في `na7n-q-slaq-account.js`. المخزن المحلي على جهاز المستخدم **لا يمكن ترحيله تلقائيًا من الخادم**.
- **اختبار Q-SLAQ الوهمي:** `public.na7n_qslaq_demo_results` و`na7n-q-slaq-demo.js` و`na7n-q-slaq-demo-account.js`: أرقام تجريبية مولدة آليًا، منفصلة عن بيانات المرضى. ينبغي عدم ضمها إلى سجلات الإنتاج.
- **صلاحيات الفريق:** `public.na7n_story_staff`، لوحات `admin-stories.html` و`na7n-stories-admin.js`، وقواعد MFA، تحتاج مراجعة مستقلة؛ لا تعتمد أسماء الأدوار فقط كضمان صلاحية.
- **قصص المرضى الطبية:** التخزين المباشر غير مُفعّل في بيئة Supabase الحالية. يجب عدم تفعيل المسودة الطبية قبل جاهزية تخزين صحي معتمد.
- **البيئة الجغرافية الحالية:** مشروع NA7N في Supabase ضمن `ap-south-1` (الهند). الهدف الإماراتي **مقترح** `me-central-1` عندما تصبح المنطقة موثوقة وتتحقق موافقات الاستضافة. قد تتطلب الظروف مزودًا محليًا آخر.

## 2. مشكلات الترحيل المتوقعة
1. **هوية الحساب:** لا تفترض إمكانية نقل كلمات مرور المستخدمين أو MFA أو الجلسات عبر نسخ قواعد البيانات. يجب اختيار مزود مصادقة واضح (AWS Cognito أو بديل موافق عليه) وكتابة خطة تحقق/إعادة ضبط آمنة.
2. **ربط الملكية:** كل نتيجة مرتبطة بمعرف مستخدم معيّن. يجب الاحتفاظ بخريطة ملكية داخل بيئة آمنة؛ لا تستخدم البريد الإلكتروني المفتوح كأساس الوحيد للملكية.
3. **التفويض:** اختبار منع المستخدم (أ) من الاستعلام عن بيانات المستخدم (ب)، بمن فيهم الحسابات المتعددة والمستعرضون المجهولون والموظفون؛ لا تكفي حماية الواجهة الأمامية.
4. **التوافر:** التصميم يحتاج API وخدمة تنفيذ وجلسات وتوقيع مفاتيح، مراقبة، تدقيق، نسخ احتياطي واستعادة، WAF وRate limits، وكلها **غير منفذة** في قالب القاعدة.
5. **إقامة البيانات:** راجع السجلات والتحليلات والنسخ والنسخ خارج المنطقة والإشعارات البريدية والتقارير والتحكم في المفاتيح؛ Region وحدها لا تضمن الامتثال.
6. **الاستبيانات:** نحتفظ بنسخة خوارزمية Q-SLAQ، والتواريخ والمقاييس الثلاثة والأسئلة واللغات ونسخة المصدر وحقول الموافقة والإصدارات، ولا نحول درجات 13/14 إلى تصنيفات سريرية غير معتمدة.
7. **بيانات التطوير:** لا تقم بترحيل إجابات وهمية إلى الإنتاج باعتبارها نتائج مرضى. أوقف إعداد التجربة قبل الإطلاق.
8. **النطاق وSEO:** أبقِ `CNAME` و`robots.txt` و`sitemap.xml` و`hreflang` دون تغيير، ما لم يثبت اختبار الانتقال غير ذلك.

## 3. مخرجات التحقق المطلوبة قبل كل عملية ترحيل
- عدد السجلات لكل جدول **مجمّع فقط** دون تسريب بيانات شخصية في سجلات الاختبار.
- تقرير اتصال الحسابات إلى النتائج مع اختبار الملكية وعدم عبور الأذونات.
- تقييم حالة البيانات الشخصية/الصحية الفعلية الموجودة حاليًا، وليس الافتراض.
- جدول mapping واضح من مخطط Supabase إلى مخطط AWS وAPI.
- جدول للنسخ الاحتياطية والتشفير ومدة الحفظ والحذف والاسترداد.
- وثيقة موافقة الأمن والقانون والمالك على النطاق والموعد وفترة التراجع.

## 4. ما لا يجب وضعه في GitHub
- أي مفتاح AWS/Supabase إداري، كلمة مرور أو رمز MFA أو بيانات عميل.
- قاعدة البيانات الحالية أو نسخ احتياطية فيها هوية أو استبيانات صحية.
- ملفات متغيرات البيئة والإعدادات التي تحتوي على رموز وصول.
- مخرجات تصدير المستخدمين أو جداول بيانات حساسة.
