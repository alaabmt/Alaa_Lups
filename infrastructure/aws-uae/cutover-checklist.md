# خطة اعتماد الانتقال والتراجع — نَحْنُ / AWS UAE
**حالة القائمة:** مسودة قابلة للتحقق، لا تصريح تشغيل. المسؤول النهائي عن اعتماد أي تشغيل هو مالك المشروع وأصحاب الاختصاص القانوني/الأمني.

## المرحلة صفر — جاهزية الحساب دون موارد مدفوعة (يمكن البدء بها الآن)
- [ ] تفعيل MFA على الحساب الرئيسي (Root)، مع حفظ وسائل الاسترداد خارج الجهاز.
- [ ] إنشاء صلاحيات إدارة يومية مناسبة بدل العمل الدائم بحساب Root.
- [ ] تشغيل تنبيهات ميزانية وفوترة، وتحديد سقف إنفاق وفئات الخدمات المقبولة.
- [ ] اعتماد أسماء الحسابات/البيئات: اختبار منفصل عن إنتاج؛ صلاحيات مراجع ومشغّل مستقلة.
- [ ] توثيق مالك الحساب، جهة الفوترة، مالك المخاطر ووسائل الاتصال في الحالات الطارئة.
- [ ] تعيين مسؤول مراجعة قانونية للبيانات الصحية ضمن الإمارات.
- [ ] لا مشاركة مفاتيح AWS أو الرموز السرية في البريد أو GitHub أو المحادثات.

## المرحلة الأولى — قرار منطقة التشغيل
- [ ] مراجعة https://health.aws.amazon.com/health/status والتأكد من عودة `me-central-1` لحالة مستقرة لفترة يحددها فريق التشغيل.
- [ ] التأكد من توافر PostgreSQL RDS وSecrets Manager وS3 وIAM ونسخ AWS Backup وتقارير التدقيق في المنطقة فعليًا.
- [ ] قياس توفّر مناطق الإتاحة ومدى تعافي AZs؛ عدم افتراض أن `MultiAZ` آمن في وضع تعطل متعدد.
- [ ] دراسة بديل استضافة داخل الإمارات وخطة استعادة **داخل الدولة** إذا استمرت أعطال المنطقة.
- [ ] اعتماد تكلفة شهرية وتكلفة الاسترداد ومخاطر انقطاع متعدد المناطق.

## المرحلة الثانية — بنية محمية (تحتاج موافقة جديدة)
- [ ] فحص القالب `cloudformation/na7n-data-foundation.yaml` ببرنامج `aws cloudformation validate-template`.
- [ ] مراجعة وصول الشبكة والمجموعات الأمنية؛ RDS بلا وصول من الإنترنت وS3 ممنوع الوصول العام.
- [ ] نشر نسخة تجريبية معزولة بعد التصريح فقط؛ تأكيد التشفير واستعادة النسخ الاحتياطي وDR.
- [ ] إضافة تقارير التدقيق، الإنذارات، تحديد معدلات الطلب، WAF، ومفاتيح KMS محكومة حسب سياسة الامتثال؛ القالب الحالي **لا ينفذ كل ذلك**.
- [ ] إنشاء API خلفي موثوق يحجب بيانات الخدمة الإدارية عن المتصفح.
- [ ] اختيار وتنفيذ هوية بديلة وصلاحيات صفوف/موارد server-side، وإعادة اختبار MFA للموظفين.

## المرحلة الثالثة — اختبارات البيانات والواجهة
- [ ] ترحيل **بيانات تجريبية بحتة** إلى staging لتجربة الأداء، دون نقل حسابات مرضى أو بيانات صحية حقيقية.
- [ ] التحقق من تسجيل الدخول والخروج واستعادة الحساب وMFA وحماية الجلسة والكوكيز.
- [ ] اختبار «حسابي» من هاتفين مختلفين بالحساب التجريبي نفسه؛ تظهر أربع نتائج Q-SLAQ بأربع تواريخ، ولا تظهر لحساب آخر.
- [ ] فحص جميع أسئلة Q-SLAQ الإجبارية الـ19 وصحة الدرجات (0–34/0–18/0–10).
- [ ] تجربة استخراج PDF يتضمن الأسئلة والأجوبة وشرح الأرقام بالعربية والإنجليزية.
- [ ] اختبارات الخصوصية والاختراق والحمل والمراقبة والنسخ والعودة بعد عطل.
- [ ] التحقق من أن `na7nlupus.com` والروابط العامة والبحث والصفحات لا تزال تعمل.

## المرحلة الرابعة — **شرط عدم البدء بمرضى حقيقيين**
- [ ] اعتماد جهة التحكم في البيانات الصحية ومالك النظام والعقود والتصاريح المطلوبة.
- [ ] موافقة موثقة على مكان المعالجة والنسخ والاحتفاظ وحذف البيانات واستجابة الحوادث.
- [ ] تدقيق مستقل للأذونات والتشفير والاحتفاظ وحق الوصول؛ لا يوجد صلاحية عامة لنتائج مستخدمين آخرين.
- [ ] تعطيل زر حفظ Q-SLAQ الوهمي وميزة إدخال التجارب إلى Supabase (feature flag في قاعدة البيانات).
- [ ] منع نسخ بيانات المرضى من المصدر القديم غير المعتمد؛ لا يُتخذ قرار ترحيلها قبل مراجعة مستقلة.
- [ ] حذف/عزل بيانات الوهميين حسب السياسة؛ لا تُقدّم أنها سجلات مرضى.
- [ ] توقيع صاحب المشروع والمختصين على قرار تشغيل (Go/No-Go).

## المرحلة الخامسة — الانتقال المنضبط عند طلبك
1. خذ نسخة احتياطية من البيانات **المصرّح بها** فقط وتحقق من إمكان استعادتها.
2. شغّل البيئة الإماراتية جنبًا إلى جنب مع البيئة القديمة، دون تغيير DNS في البداية.
3. نفّذ هجرة هوية الحسابات ومراجعات الأذونات وآلية إعادة تسجيل الدخول عند الحاجة، دون افتراض نقل كلمات المرور والجلسات.
4. تحقق من سجلات القياس والتدقيق وسلامة حسابات الاختبار وظهور النتائج.
5. افتح الوصول تدريجيًا وفق خطة محددة وراقب الأعطال والخصوصية والأداء.
6. بدّل الاتصال بالخلفية عبر إعداد معتمد، وغيّر DNS **فقط إذا انتقل موقع الويب نفسه**؛ قد يبقى GitHub Pages كما هو.
7. أبقِ خطة الرجوع جاهزة، واحتفظ بنطاق بيانات المراحل منفصلًا حتى إعلان اكتمال النقل.
8. راقب دورة تشغيل كاملة قبل إغلاق مصدر مصرح به.

## إجراء التراجع
- إذا فشل تسجيل الدخول أو ظهرت نتائج مستخدم آخر أو أخفقت الاستعادة **أوقف الانتقال فورًا**.
- أغلق الكتابة إلى الوجهة غير الصالحة بدل محاولة التزامن العشوائي ثنائي الاتجاه.
- أعد توجيه واجهة المستخدم إلى آخر خدمة تم التحقق منها **إذا كان ذلك قانونيًا ولا يكشف بيانات صحية**.
- لا تعد إرسال بيانات صحية إلى استضافة Supabase الهندية لمجرد استعادة الخدمة.
- وثّق الحادث وتوقيته والمسؤول والتأثير وما تم حذفه/استرداده.
- حل مشكلة التباين بين المصدرين قبل أي محاولة ثانية؛ لا تفترض أن الرجوع مجرد تغيير DNS.

## قرارات لا تزال معلقة
- **قرار A:** هل تبقى الصفحات العامة على GitHub Pages أم تنقل إلى خدمة استضافة إماراتية؟
- **قرار B:** مزود تسجيل الدخول الجديد ومعالجة كلمة المرور والجلسات ومفاتيح MFA.
- **قرار C:** خطة توافر واستمرارية أعمال محلية في ضوء اضطراب AWS UAE.
- **قرار D:** التكلفة/الميزانية والمعيار المقبول للتعطل وفقدان البيانات (RTO/RPO).
- **قرار E:** توثيق الامتثال القانوني وموافقات المراجعة الطبية والمحتوى والتحكم في البيانات.
- **قرار F:** يوم الانتقال ومدة التجربة المباشرة والمراجعة النهائية.
